# ADR-T007: Subsonic authentication via app passwords

**Status:** proposed
**Date:** 2026-10-17

## Context

Subsonic's token authentication sends `t = md5(password + salt)`. To verify it, the server must be able to recover the password. Storing users' main passwords in recoverable form is not acceptable. OpenSubsonic adds an `apiKey` extension that avoids the problem, but many clients only support token or plain-password authentication.

## Decision

- Users' main passwords are hashed with Argon2id and are never usable through the Subsonic API.
- Subsonic clients authenticate with per-client **app passwords**. These are generated by the server, stored encrypted with a server-held key, and can be revoked individually.
- The OpenSubsonic `apiKey` extension is supported and preferred for clients that implement it.
- The first-party API and web player use sessions, as in the Go implementation's identity design.

## Alternatives considered

- **Store main passwords in recoverable form.** What many Subsonic servers do. A database leak would expose every user's password.
- **Support only the `apiKey` extension.** Cleanest, but rules out too many existing clients.

## Consequences

- A leaked app password exposes one client's access, which can be revoked. It never exposes the main password.
- The server needs an encryption key at rest, generated on first run alongside the session-signing key.
- The web player needs a screen for creating and revoking app passwords.
